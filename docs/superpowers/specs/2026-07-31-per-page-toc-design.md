# weoc-ui-doc: per-page table of contents (pilot)

**Date:** 2026-07-31
**Status:** Piloted on 3 pages, ready for mechanical fan-out to the rest
**Scope:** Docs site (`weoc-ui-doc`) only. Builds directly on the deep-search work
(`2026-07-31-deep-search-design.md`, implemented in `bao-weoc-ui-updates`) — that spec's
own "Open items" section flagged this exact feature as reusing its section-id scheme
rather than inventing a new one, which is what this pilot does.

## Background

Every `docs/docs/*.html` page's content is already split into `.docs-section-title`
blocks, each carrying a **stable `id`** (`tools/build-search-index.js` injects one if
missing, and by now every page has been indexed at least once). That id is exactly the
anchor target a table-of-contents needs — nothing about section identity had to be
invented for this feature; it was already a byproduct of deep search.

Two things from the existing codebase shaped every decision below:

- **`weoc-ui.js` already ships a fully declarative overlay system** — `data-wui-toggle`,
  `data-wui-anchor`, `data-wui-open-class`, `data-wui-dismiss` — bound once, globally, at
  parse time (`WUI.open`/`WUI.close`/`WUI.toggle`, `weoc-ui.js` ~L750-890). `wui-dropdown`
  and `wui-fab` are existing primitives (see `overlays.html`'s "wui-dropdown" section and
  `buttons.html`'s "wui-fab" section for the reference markup). None of this needed
  reimplementing or even a page script to wire up open/close.
- **`docs-shell.js` already has a proven click → scroll → flash pattern** for jumping to
  a `#sectionId` on the current page: the same-page branch of the deep-search click
  handler (`bindSearch()`, capture-phase listener on `[data-search-hit]`) calls
  `history.pushState(null, '', href)` then `scrollToHashTarget(true)`, which does
  `target.scrollIntoView({behavior:'smooth', block:'center'})` plus a
  `.docs-search-target-flash` CSS class (1.2s box-shadow pulse, `docs-style.css`
  ~L660-664). This is reused verbatim, not re-implemented, for TOC clicks.

## Decision

A small **floating trigger + declarative dropdown panel**, built entirely from markup
(no bespoke open/close JS), with exactly **one** new piece of centralized logic in
`docs-shell.js`: a delegated click handler that turns a `[data-toc-link]` click into the
existing scroll+flash behavior. Everything else — including every TOC label's text — is
generated by copy-pasting each page's own section titles, reusing their i18n keys as-is.

### Why not alternatives considered

- **A right-margin sticky rail** (classic "on this page" sidebar many docs sites use):
  rejected for the pilot. `.docs-page` is a centered column with a fixed `max-width`
  inside a fluid `#docs-main`; a sticky rail needs either JS-measured positioning or a
  layout change to `#docs-split`'s grid (`docs-style.css` ~L24-27), and would overlap the
  existing left nav rail on medium viewport widths. The floating-button approach needs
  zero layout changes to the shared shell.
- **A new Alpine component per page** (matching the `PAGE_INIT` → `Alpine.data()`
  pattern used for pages with real interactive state, e.g. `chartsPage()` in
  `charts.html`): rejected. The TOC has no reactive state — the entry list is static
  per page and the open/close is already handled by `weoc-ui.js`'s global delegate. Adding
  an `Alpine.data()` registration per page would mean copy-pasting the same ~10-line
  click handler into all ~29 pages instead of writing it once.
- **A per-page inline `<script>` for the click handler**: rejected for the same DRY
  reason — the scroll+flash logic is 100% generic (works identically for any page, any
  section id), so it belongs in one place, not duplicated 29 times. This is the one
  deliberate `docs-shell.js` touch this pilot makes (see "Why `docs-shell.js`" below) —
  everything else is page-local markup.
- **Scrollspy (highlight the current TOC entry as the user scrolls)**: rejected as
  out of scope for the pilot — it needs an `IntersectionObserver` per page and is a
  materially bigger surface to get right (and to fan out) for a "does clicking work"
  pilot. Left as a documented future enhancement (see Open items).

### Why `docs-shell.js` gets touched (and NAV does not)

The task brief for this pilot flagged that NAV-array changes should be justified if
needed. This pilot does **not** touch the `NAV` array — a TOC is in-page, not a site
navigation entry, and `renderSidebar()`/`renderChrome()` are untouched. The one
`docs-shell.js` change is a new `bindTocLinks()` function (mirrors `bindSearch()` /
`bindHtmxNav()`'s own bind-once pattern, called once from `DocShell.init()`), plus the
one-line call site. It exists because:

1. Without it, every TOC link would need `hx-boost="false"` (already added, to stop
   htmx trying to "navigate" to a same-page hash) **and** its own preventDefault +
   scroll + flash logic — and that logic is identical on every page.
2. `docs-shell.js` itself is loaded once and outlives every SPA swap (same reasoning
   `bindSearch()`/`bindHtmxNav()` already rely on), so a bind-once global delegate is
   the natural fit — it never needs re-binding per page and needs no `Alpine.data()`
   ceremony.

## Architecture (the pattern to fan out)

### 1. Markup — first child of `.docs-page`

Insert immediately after `<div class="docs-page" ...>` opens (before any page-local
`<style>`/`<script>` that page already has), so the insertion point is always the same
regardless of what else is on the page:

```html
<button type="button" class="wui-fab primary wui-fab-fixed-br" data-wui-toggle="#docs-toc-panel" aria-haspopup="true" aria-expanded="false" data-wui-i18n-attr="aria-label:docs_<page>_<N>">
  <span class="material-symbols-outlined">toc</span>
</button>
<div id="docs-toc-panel" class="wui-dropdown docs-toc-panel" data-wui-open-class="show" data-wui-anchor="top-end" hx-boost="false">
  <div class="docs-toc-panel-hd">
    <span class="material-symbols-outlined">toc</span>
    <span data-wui-i18n="docs_<page>_<N>">On this page</span>
  </div>
  <nav class="docs-toc-list" data-wui-i18n-attr="aria-label:docs_<page>_<N>">
    <a href="#<sectionId>" class="docs-nav-item" data-toc-link data-wui-dismiss="" data-wui-i18n-html="docs_<page>_<M>"><span class="material-symbols-outlined"><icon></span><Title></a>
    <!-- one <a> per .docs-section-title on the page, same order -->
  </nav>
</div>
```

Key choices baked into that shape:

- `wui-fab primary wui-fab-fixed-br` — an existing primitive, unmodified. `position:
  fixed` relative to the viewport (`weoc-ui-interactive.css`), so it needs no
  positioning wrapper and survives page scroll.
- `data-wui-anchor="top-end"` — opens **upward** (trigger sits at the bottom) and
  **end-aligned** (hugs the same screen edge the fixed trigger already hugs,
  RTL-mirrored automatically by `WUI.anchor()`).
- `hx-boost="false"` on the panel — without it, `#docs-split`'s `hx-boost="true"`
  (set in `DocShell.init()`) would intercept every `<a href="#id">` click and have htmx
  try to "navigate" to it.
- `data-wui-dismiss=""` on every entry — closes the panel on click via `weoc-ui.js`'s
  own bubble-phase dismiss listener; `bindTocLinks()`'s capture-phase-independent
  handler (registered without `stopPropagation()`) runs alongside it, not instead of it.
- **Each entry's `data-wui-i18n-html` id is the exact same key as that section's own
  `.docs-section-title`** — not a new key. This is the biggest fan-out time-saver: zero
  new translation strings needed for the entries themselves, and the TOC label is
  guaranteed to always match the section title verbatim (icon included), in both
  languages, forever, with no drift possible.
- `.docs-nav-item` (existing sidebar-nav class, `docs-style.css` ~L228-248) is reused
  as-is for entries — same colors/hover/active states as the real sidebar, zero new
  item-level CSS. Only a scoped layout override was added (`.docs-toc-list
  .docs-nav-item { display:flex; ... }`, `docs-style.css`) so the leading icon sits
  inline instead of stacking (`.docs-nav-item`'s base `display:block` was written for
  icon-less sidebar links).

### 2. CSS — shared, not per-page

Added once to `docs-style.css` (not duplicated per page): `.docs-toc-panel` (width +
max-width clamp), `.docs-toc-panel-hd` (heading row), `.docs-toc-list` (
`max-height: min(60vh, 420px); overflow-y:auto` — needed once a page passes roughly
15+ sections; `charts.html`'s 21-entry list is the pilot's stress test for this), and
the `.docs-toc-list .docs-nav-item` icon-layout override above. Fan-out pages need
**zero** new CSS — this block already covers every page.

### 3. JS — one shared delegate, zero per-page script

`docs-shell.js`: `bindTocLinks()` (new, ~15 lines) + one call from `DocShell.init()`.
Fan-out pages need **zero** new JS. The full click path:

```
click [data-toc-link]
  → preventDefault()
  → history.pushState(null, '', href)         // URL reflects #sectionId, back/forward works
  → scrollToHashTarget(true)                   // existing fn: scrollIntoView + flash
weoc-ui.js's own bubble-phase [data-wui-dismiss] listener (unrelated call) closes the panel
```

### 4. i18n — one new key per page

Every page needs exactly **one** new i18n id (not one per entry — see above): the
"On this page" panel heading, reused via `data-wui-i18n` on the heading text and
`data-wui-i18n-attr="aria-label:<key>"` on both the trigger button and the `<nav>`.
Piloted values: `docs_containers_64`, `docs_charts_84`, `docs_views_59` (each page's
next-available id, appended to that page's `docs/i18n/<page>.js`) — en `'On this page'`,
ar `'في هذه الصفحة'`.

**Only pages already in `docs-shell.js`'s `I18N_PAGES` array are ready for this.** A page
outside that list (e.g. `typography.html`, `buttons.html`, `navigation.html` at the time
of this pilot) has `.docs-section-title` elements carrying `data-wui-i18n-html` ids that
currently resolve to nothing — the site silently falls back to the authored English text
for the *whole page*, not just the TOC. Fanning the TOC out to one of those pages doesn't
break anything (same silent-fallback behavior extends to the TOC's reused keys), but it
also won't be bilingual until that page gets a real `docs/i18n/<page>.js` file — a
pre-existing gap, not something this pilot needed to fix.

## Fan-out recipe (mechanical, for the remaining ~26 pages)

For each `docs/docs/<page>.html`:

1. `grep -n "docs-section-title" docs/docs/<page>.html` — get each section's `id`,
   `data-wui-i18n(-html)` key, leading `<span class="material-symbols-outlined">icon</span>`,
   and visible title text, in document order.
2. Find the page's next free i18n id: `grep -o "docs_<page>_[0-9]*" docs/i18n/<page>.js | sort -t_ -k3 -n | tail -1`, add 1.
3. Insert the markup block from "Architecture §1" as the first child of
   `<div class="docs-page" ...>`, filling in the trigger's/panel's/nav's
   `aria-label`/heading key with the id from step 2, and one `<a>` per section from
   step 1 (same id/key/icon/text, wrapped in the fixed `data-toc-link data-wui-dismiss=""`
   attributes).
4. Append one line to `docs/i18n/<page>.js`: `{lang:'en', id:'docs_<page>_<N>',
   value:'On this page'}, {lang:'ar', id:'docs_<page>_<N>', value:'في هذه الصفحة'}`.
5. No CSS, no JS, no `docs-shell.js` change, no `NAV` change, no `search-index.json`
   change (the TOC block sits before the first `.docs-section-title` match, so
   `build-search-index.js`'s section-boundary scan never sees it — confirmed by running
   the indexer after the pilot's edits and diffing `search-index.json`: no change).

Steps 1-2 are mechanical enough to script (parse `.docs-section-title` divs the same way
`tools/build-search-index.js`'s own `extractSections()` already does) if fanning out to
many pages at once; the pilot did them by hand for 3 pages since that was faster than
writing a generator for a 3-page sample.

## Pages piloted

- `containers.html` — 12 sections (medium; the task brief's own suggested example).
- `charts.html` — 21 sections (longest page in the site; stress-tests the scrollable
  panel's `max-height`/`overflow-y`).
- `views.html` — 4 sections (shortest already-bilingual page; panel never needs to
  scroll).

`typography.html`/`buttons.html`/`navigation.html` were considered for the "short page"
slot but rejected — none are in `I18N_PAGES` yet (see i18n note above), and piloting
against an already-broken-bilingual page would have made it harder to tell a real
regression from a pre-existing gap.

## Testing / verification performed

Live in-browser (`claude-in-chrome`), local static server over the worktree, all 3 pages:

1. Hard-loaded each page directly → TOC trigger renders, opens/closes, all entries
   present with correct icons/labels.
2. Clicked entries at the start, middle, and end of each page's list (including
   `charts.html`'s last entry, `destroy()`, after scrolling the 21-item panel) →
   correct section scrolled into view (`block:'center'`) and `location.hash` updated
   via `pushState`.
3. **Navigated to each page via an in-app sidebar/htmx SPA link (not a hard reload)** —
   the exact class of bug this project hit before or the "content outside the swap
   target never travels" bug — TOC still rendered and worked identically post-swap.
4. Toggled EN ⇄ AR — panel heading, aria-labels, and every entry's label (icon +
   text) all flip languages live, panel re-anchors to the mirrored screen edge under
   RTL (checked `containers.html` in both directions).
5. `read_console_messages` after each interaction on all 3 pages: zero errors/exceptions
   (one unrelated Chrome-extension log line, not from the page).

## Concerns / open items (deliberately out of scope for the pilot)

- **Scrollspy** (highlighting the TOC entry matching the currently-scrolled section) —
  not implemented; would need an `IntersectionObserver` per page. Worth adding once the
  static version has shipped everywhere, not before.
- **Non-bilingual pages** (`typography.html` and others outside `I18N_PAGES`) need their
  own `docs/i18n/<page>.js` before their TOC (or anything else on the page) is truly
  bilingual — pre-existing gap, unrelated to this feature, flagged here so the fan-out
  agent doesn't assume every page is i18n-ready.
- **A future generator script** (per "Fan-out recipe" above) would remove essentially
  all manual-transcription risk (typo'd section id, mismatched icon) for the remaining
  ~26 pages — recommended if fanning out in one batch rather than a few pages at a time.
